# Ciclo 05 — Pricing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` to implement independent tasks after contracts and database boundaries are frozen. Steps use checkbox syntax.

**Goal:** Deliver App 02 product, combo and channel pricing with exact calculations, owner-scoped persistence, recipe-cost integration and immutable simulation history.

**Architecture:** Keep calculation in a new pure `@donos/domain-pricing` package; use versioned Zod contracts, the existing Fastify API and Postgres/RLS, and the existing Vite Precificação shell. The backend enforces `pricing_core`; recipe cost reuses the existing recipe service and separately enforces `inventory_core`. The UI never calculates authoritative money or accesses database tables.

**Tech Stack:** Existing TypeScript, pnpm workspaces, Zod 4, Fastify 5, PostgreSQL `numeric`, React/Vite, Vitest and Playwright. No new dependency is planned.

**Spec:** `docs/superpowers/specs/2026-10-16-pricing-design.md`

## Global Constraints

- Respect DONOS Next V3 DEC-001 through DEC-013 and criteria T-15 through T-18.
- `organization_id` is the primary boundary; validate owner and `restaurant_id` in API and RLS. No employee profiles/RBAC.
- Money and quantities are decimal strings/integers/ratios; no critical `number` arithmetic. Price suggestion rounds up to BRL cent and all output metrics recalculate from that final price.
- App 02 works with `pricing_core` and manual cost alone. Recipe cost integration requires same-owner `inventory_core`, location and validated recipe state.
- Recipe/stock cost remains authoritative in App 01. Never query its tables from the browser or duplicate its valuation algorithm.
- Simulations are append-only snapshots. Writes are idempotent, transactional and audited.
- Never touch legacy, production, old Vercel/domains, billing, paid integrations or WhatsApp. Supabase DEV use for Cycle 05 is not authorized by the Cycle 04 decision.
- Pin any new dependency and update lockfile only with explicit rationale; none is planned.
- Do not run DB integration/migration against hosted DEV until the founder explicitly authorizes the exact DONOS Next DEV project for this cycle. Tests under `tests/helpers/local-db.ts` currently load hosted DEV credentials; do not run them as if local. Use an isolated local database or stop at this gate.

## Decision Gate Before Code

Resolved 2026-10-16: founder approved IMP-016, IMP-017 and the current validated-recipe/local semantics; recorded in `docs/05-REGISTRO-DE-DECISOES.md`, `docs/DECISIONS.md` and `docs/adr/0004-pricing-incidence-and-combos.md`. Implement exactly these rules:

- **IMP-016:** margin and CMV denominators use sale revenue after commercial discount and before fee/tax deductions; each percentage fee/tax explicitly declares whether its base is list price or post-discount price; the scenario's fixed fees apply once per sold product/combo. Use the V3 shortcut only when bases are equivalent and there is no discount; otherwise solve the declared bases deterministically. No order-level fixed-fee allocation in this cycle.
- **IMP-017:** recipe cost responses expose an exact per-component packaging breakdown; combo overrides identify only the packaging component paths they replace, preserving all other costs. Combo-exclusive packaging is added once; channel fee applies once per combo sale.
- Confirmed: product stores only `recipeId`, selected `locationId` and `quantityPerSale`; each simulation resolves the current validated recipe version and snapshots `recipeVersionId`, source, calculation time, cost and component breakdown.

If an approved incidence/base cannot be represented exactly by the contract, stop and update the ADR/spec/plan before implementing dependent code. Taxes remain manual owner-entered values with accounting support; no tax regime is inferred.

## Review Focus

1. **Different discount, fee and tax bases:** a reasonable owner expects the exact configured incidence or a clear refusal, never an approximate formula. Test in `pricing-calculation.test.ts` with gross 50, discount 10%, and fee 10%; pin the approved base (R$5.00 on gross or R$4.50 after discount).
2. **Recipe absent, unvalidated or from another tenant/unit/location:** owner expects explicit unavailable/manual choice and no cross-tenant data. Test `pricing-api.test.ts` and `pricing-tenant-security.test.ts`.
3. **Combo package override:** owner expects replacing one selected package while retaining all other ingredient/packaging costs. Test replacement, no replacement and exclusive packaging in `pricing-calculation.test.ts` and API integration.
4. **Duplicate/retried simulation:** owner expects one immutable snapshot for one idempotency key and a conflict for a different payload. Test `pricing-api.test.ts`.
5. **Concurrent or expired entitlements/context:** owner expects no price/cost disclosure or write after the gate expires. Test `pricing-tenant-security.test.ts` and module-access regression.

**Interfaces frozen for later tasks:**
- `PricingRateInput`: `{ id: string; kind: 'fee'|'tax'|'discount'; mode: 'percentage'|'fixed'; value: DecimalString; rateBase: 'list_price'|'net_after_discount'|null; fixedBasis: 'per_sale' }` (amend only if approved IMP-016 changes the bases; percentage discounts use list price; fixed entries have `rateBase:null`).
- `PricingMoneyString`: canonical BRL amounts using `InventoryValueStringSchema` precision (up to 26 integer digits and 12 fraction digits). Percentages and quantities use their existing canonical schemas. Exact internal products/sums use bigint rationals; only displayed quote price rounds upward to cent.
- `ExactMoneyRatio`: `{ numerator: CanonicalUnsignedIntegerString; denominator: CanonicalPositiveIntegerString }`, value in BRL is `numerator / denominator / 10^12`. GCD-reduced; each integer string is bounded to 256 digits, with explicit `NUMERIC_RANGE` on overflow. This is a pricing/recipe wire contract and does not import inventory-domain types.
- `PricingCostComponent`: `{ componentPath: string[]; role: 'ingredient'|'packaging'; costPerFinalUnitExact: ExactMoneyRatio }`. Recipe components and total reconcile exactly as rational values; the existing rounded `costPerFinalUnit` remains display-only. Adapt manual ingredient to a reserved stable path and each package to `[packageId]`. Recipe values are scaled to one sale with rational arithmetic; do not round components.
- `PricingPackagingInput`: `{ id:string; name:string; costPerSale:PricingMoneyString }`; map manual packaging to the stable path `[id]`. Manual ingredient cost and manual packaging stay separate so the UI cannot add packaging invisibly to both cost buckets.
- `ManualCostSourceInput`: `{ kind:'manual'; ingredientCost:PricingMoneyString; currency:'BRL' }`; `RecipeCostSourceInput`: `{ kind:'recipe'; recipeId:string; locationId:string; quantityPerSale:QuantityString }`, where quantity uses the current recipe output unit and scales the recipe cost/components to one sale.
- `PricingVariantCostSource`: manual `{ kind:'manual'; ingredientCost: PricingMoneyString; currency:'BRL'; updatedAt:string }` or recipe link `{ kind:'recipe'; recipeId:string; locationId:string; quantityPerSale:QuantityString }`. A variant stores a link only, never stale recipe cost.
- `PricingCostSourceSnapshot`: manual `{ kind:'manual'; ingredientCost:PricingMoneyString; currency:'BRL'; updatedAt:string }` or recipe `{ kind:'recipe'; recipeId:string; recipeVersionId:string; locationId:string; calculatedAt:string; unitCostExact:ExactMoneyRatio; unitCostDisplay:PricingMoneyString; components:PricingCostComponent[] }`. The pricing contract owns this wire DTO and does not import recipe-domain types. Every simulation refreshes recipe cost through the central recipe service; historical snapshots retain the version/cost used.
- `PricingCalculationInput`: `{ ingredientCostExact:ExactMoneyRatio; packagingCostExact:ExactMoneyRatio; otherVariableCost:PricingMoneyString; rates:PricingRateInput[]; targetContributionMargin:DecimalString|null; targetCmv:DecimalString|null; listPrice:PricingMoneyString }`.
- `PricingComboCostInput`: `{ components:Array<{ variantId:string; quantity:QuantityString; costComponents:PricingCostComponent[]; otherVariableCostPerSale:PricingMoneyString; replacedPackagingPaths:string[][] }>; exclusivePackaging:PricingPackagingInput[] }`. Component costs come from the selected cost-source snapshot; only package paths explicitly listed for replacement are excluded. Manual ingredient/package paths are stable IDs.
- `calculateComboCost(input: PricingComboCostInput): { ingredientCostExact:ExactMoneyRatio; packagingCostExact:ExactMoneyRatio; otherVariableCostExact:ExactMoneyRatio; totalCostExact:ExactMoneyRatio }` counts only the listed packaging paths as replaced and preserves all other paths.
- `PricingQuote`: `{ status:'available'|'unavailable'; reason:string|null; suggestedPrice:PricingMoneyString|null; costBuckets:{ingredients:PricingMoneyString;packaging:PricingMoneyString;otherVariable:PricingMoneyString}; totalVariableCost:PricingMoneyString; currentPriceMetrics:{netRevenue:PricingMoneyString;contributionMargin:DecimalString;cmv:DecimalString}|null; suggestedPriceMetrics:{netRevenue:PricingMoneyString;contributionMargin:DecimalString;cmv:DecimalString}|null; rateBreakdown:Array<{rateId:string;base:PricingMoneyString|null;amount:PricingMoneyString}> }`. Cost buckets, current/list-price metrics and suggested-price metrics remain separately visible in the response/simulation snapshot.
- `CreatePricingProductInput`: `{ name:string; description:string|null }`; `CreatePricingVariantInput`: `{ name:string; listPrice:PricingMoneyString; costSource:ManualCostSourceInput|RecipeCostSourceInput; packaging:PricingPackagingInput[]; otherVariableCost:PricingMoneyString }`; `CreatePricingChannelInput`: `{ name:string; rates:PricingRateInput[] }`; `CreatePricingComboInput`: `{ name:string; components:Array<{variantId:string; quantity:QuantityString; replacedPackagingPaths:string[][]}>; exclusivePackaging:PricingPackagingInput[] }`; `CreatePricingSimulationInput`: `{ variantId:string|null; comboId:string|null; channelId:string; targetContributionMargin:DecimalString|null; targetCmv:DecimalString|null }` (exactly one of `variantId`/`comboId`).
- `calculatePricingQuote(input: PricingCalculationInput): PricingQuote` is pure; errors use `PricingCalculationError` codes for invalid target, non-positive denominator, invalid rate base, missing cost component and numeric range.
- Contracts include `CreatePricingProductInput`, `UpdatePricingProductInput`, `CreatePricingVariantInput`, `UpdatePricingVariantInput`, `CreatePricingChannelInput`, `CreatePricingComboInput`, `CreatePricingSimulationInput`, DTOs `PricingProduct`, `PricingVariant`, `PricingChannelProfile`, `PricingCombo`, `PricingSimulation` and `PricingQuote`.
- DTO shape: `PricingProduct` has `id,name,description,archivedAt,variants` where each variant summary has `id,name,listPrice,status`; `PricingVariant` has `id,productId,name,listPrice,costSource,packaging,otherVariableCost,archivedAt`; channel/combo DTOs contain their normalized rates/components; `PricingSimulation` contains identifiers, input snapshots, exact cost-source/channel/combo snapshots, quote and `createdAt`. Lists are cursor-paged; product list includes only summaries, not full cost-source DTOs.
